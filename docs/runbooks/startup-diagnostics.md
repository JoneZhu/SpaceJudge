# SpaceJudge 首次打开与启动诊断

这套流程区分系统尚未放行程序、应用启动后初始化失败、以及界面已就绪三个阶段。应用埋点属于本轮源码改动，不在已经发布的 v0.5.3 包中；独立采集脚本也能检查旧包。增加日志不代表首次打开问题已修复。

## 采集工具

在 macOS 终端、源码仓库根目录运行以下命令。脚本依赖系统 `/usr/bin/ruby` 和 macOS 自带工具，不需要安装 Node 或使用 sudo。如果系统没有 Ruby，先停止并报告环境，不要求用户修改安全设置来运行诊断。

查看当前状态与最近十分钟的日志：

```sh
/usr/bin/ruby scripts/diagnostics/capture-launch.rb --mode snapshot
```

准备复现时，先开始实时采集：

```sh
/usr/bin/ruby scripts/diagnostics/capture-launch.rb --mode watch --minutes 10
```

等终端显示“采集已启动”，再手动打开 App。`--minutes` 允许 1–120；snapshot 表示历史时间范围，watch 表示实时采集窗口，结束后补充历史日志和状态。Ctrl+C 会停止采集子进程并保留部分 manifest；不会终止 SpaceJudge。若中途停止，后续需要再运行一次 snapshot 保存恢复后的状态。

默认输出到系统临时目录下一个新建的 `SpaceJudge-launch-…` 目录。需要长期保存时，将 `--output-parent` 指向一个已存在的、本地私密目录；每次仍会新建唯一子目录，不覆盖旧证据。不要选择应用包内部或 SpaceJudge 的扫描缓存作为保存位置。

```sh
/usr/bin/ruby scripts/diagnostics/capture-launch.rb --mode snapshot --minutes 20 \
  --app /Applications/SpaceJudge.app \
  --output-parent /absolute/private/diagnostics
```

目录为 0700，文件为 0600。manifest 列出每项命令、时间、退出码、输出量和状态；`ok` 只表示该命令执行成功。`complete` 表示采集流程走完，不表示所有命令成功或所有事件完整。

| 状态 | 含义 |
| --- | --- |
| `failed` | 命令退出失败、工具缺失或权限不足，结合对应输出判断 |
| `timeout` | 超过该项命令的时间限制，结果可能不完整 |
| `output_limit` | 输出超过 32 MiB 软上限后停止；每 0.1 秒检查，可能短暂超出 |
| `interrupted` | 用户中止，保留已采集的现场 |

退出码 0 表示流程完成且命令成功；未找到 SpaceJudge 进程的 `pgrep` 退出码 1 是允许的“当前没有该进程”。退出码 2 表示部分采集或有命令失败；退出码 1 表示参数、应用或输出位置无法使用。日志文件为空不证明没有事件，系统日志可能未持久化、已过期或没有读取权限。

## 收集内容与隐私

脚本只读取应用版本、主程序 SHA256、签名验证、隔离与来源属性、文件 inode 与时间、系统版本和启动时间。只对名称匹配且可执行文件路径与指定 App 一致的进程获取状态与一秒采样；不对其他同名程序采样。最多检查八个匹配进程，超出时会标记截断。

系统日志包含 `syspolicyd`、`authd`、`coreauthd`、`coreautha`、`amfid`、系统授权界面和会话状态。`coreauthd` 与 `coreautha` 用来区分凭据验证、并发认证请求暂存、回调与最终策略批准；单独看到密码验证成功，不代表 Gatekeeper 已完成放行。授权记录往往没有 SpaceJudge 名称，因此不能只按名称过滤。原始证据可能带有本机用户名、路径、下载 URL、其他应用的授权事件及进程堆栈，不是匿名日志。不要把整个目录上传到公开 issue；先筛选、脱敏，只分享相关片段。脚本不会打包上传，也不会读取扫描数据库或文件内容。

脚本不执行 App、不退出 App、不扫描、不重新签名、不删除隔离属性、不修改完全磁盘访问、Gatekeeper 或 SIP。它不执行可能影响后续评估状态的 `spctl` 或 `syspolicy_check`。它可能终止的只有自己创建的采集命令及其子进程，原因是超时、输出限制或用户中止。

## 应用启动事件

新源码通过 Unified Logging 输出 JSON，subsystem 为 `com.hongdazhu.SpaceJudge`，category 为 `Startup`。每次进程运行有独立 `session`，相同会话按 `sequence` 排序。`timestampUTC` 是 UTC 墙上时间；`elapsedMilliseconds` 是从日志对象初始化起的连续时钟时间，包含睡眠经过时间，不能解释为 CPU 运算时间或从 Finder 点击起的时间。阶段耗时可用同一会话两个记录相减。

主要顺序：`processEntry` → `appDidFinishLaunching` → `bootstrapStarted` → `workspacePrepareStarted` / `workspacePrepared` → `writerOpenStarted` / `writerOpened` → `readerOpenStarted` / `readerOpened` → `repositoriesReady` → `modelReady`。`rootViewAppeared` 表示 SwiftUI 根视图出现，可以早于模型准备完成；不表示扫描完成，也不是像素绘制的独立证明。

失败使用 `bootstrapFailed`，只带 workspace、sqlite、store、cocoa、posix 或 unknown 分类和允许的数值码。程序不会记录错误文字、error domain、缓存路径、文件名、扫描目录或扫描结果。阶段为 notice，失败为 error，不依赖开启 debug 才记录；仍受系统日志保存策略限制。

## 受控复现

复现重点是用户报告的“安装后首次打开及批准”路径，不是日常扫描。开发构建、从源码目录直接启动、已批准后的再次打开都不能替代首次下载安装验证。首次安装、覆盖更新和同一安装的再次打开必须分别记录。

1. 保留下载包和安装位置；记录系统版本、版本与 build、下载方式和是否曾批准过该副本。避免同时运行 DMG 内和 Applications 内的两个副本。
2. 在任何打开或批准操作前开启 watch，等采集开始。记下点击“仍要打开”、身份验证和后续确认的时间，不能只记“给过权限”。
3. 如果无响应，先另开终端运行 snapshot，保留 PID、启动时间和堆栈。不要重装、重新签名或删除隔离属性来清除现场。
4. 保存工作后，可以手动锁屏再解锁作一次对照；只在受控复现中试验，不把它宣传成可靠修复。记下锁屏、解锁、界面出现的时间，再运行 snapshot。
5. 按相同 PID、路径、文件身份、会话和校验和串联事件，检查批准是否完成、系统何时放行、应用入口何时出现。授权后仍卡住，再沿应用阶段找最后一个开始但未完成的步骤。

已经批准的本机不能通过普通退出再打开证明首次安装可靠。需要新环境时，优先在另一个测试 Mac 或全新 macOS 测试虚拟机中走真实浏览器下载、DMG 拖入 Applications、首次打开与单应用批准的完整路径。不要清空工作机器的系统安全数据库、全局授权配置或移除隔离属性来伪造首次安装。测试环境须另行准备，本轮不自动创建、重置或更改主机安全状态。

没有 `processEntry` 时先看系统授权和进程采样，不能仅凭缺日志断言 App 从未运行。有入口但没有数据库完成事件时，再定位缓存或 SQLite。根视图和模型就绪后仍有问题，应转入界面或扫描诊断，不混同为首次启动失败。

## 当前调查结论

2026-10-10 的本机证据显示：同一主程序在凌晨尝试启动后发生打开请求超时；早上解锁验证成功，系统随即完成用户批准、清除启动拒绝记录，原 PID 随后进入应用并创建数据库。期间没有重启，主程序 SHA256 与此前失败时一致。这支持“未完成的授权流程在解锁后恢复”的解释，但没有完整证明最初为什么挂起，也没有证明其他 Mac 可用同一方式恢复。

本轮验证分开记录编译与单元测试、隔离开发启动、真实首次下载授权。前两项通过不能替代第三项；尚未复现前不标记“已修复”。原始本机证据只保存在忽略的本地输出目录中。

## 本轮验证结果

2026-10-10 的源码验证包括 601 项 Swift 测试通过，其中新增启动记录测试覆盖顺序、并发、UTC 时间、错误脱敏与版本字段限制。独立采集工具的 14 项 Ruby 测试、89 个断言通过，另有 5 项原安装引导检查及 146 项发布脚本回归检查通过。Debug 构建和包含 arm64、x86_64 的 Release 构建均通过；Intel 本次仅编译，未实机运行。

独立工具对当前已安装版本的 snapshot 采集完成，30 项命令成功，目录与文件权限符合约定。随后一分钟 watch 在开发构建上采到了实际启动、失败与退出事件；未签名开发包的两项签名验证失败如实写入 manifest，采集进程未掩盖失败。后续增加文件身份采集，不改变这些历史验证的命令数量。

上述 2026-10-10 的结果证明埋点和采集路径可用；当时尚未完成带埋点版本的真实浏览器下载、DMG 安装、首次批准复现，没有替换 Applications 内的应用、修改系统安全状态、重置当前授权或发布新版。

## 2026-10-11 本机安装与授权后挂起复现

在用户明确要求的现有物理 Mac 上测试，未使用虚拟机。先按用户授权移走 SpaceJudge 自身安装及数据、重置自身 TCC 权限，再通过 Safari 下载内容相同的本机诊断 DMG，使用 Finder 安装 build 9。下载和安装副本均有真实浏览器 quarantine 属性，安装包校验和及主程序身份已核对，严格深度签名验证通过。该路径触发了应用专属 Gatekeeper 拦截与“仍要打开”，但不声称已清除历史 Gatekeeper 批准缓存，也不等价于首次在另一台 Mac 从 GitHub 下载。

截至 23:19 左右的历史日志采集，未观察到该暂存请求最终返回成功或 `syspolicyd` 完成放行。随后用户完成一次锁屏、密码解锁，实时日志捕获到原请求恢复和系统放行；原 PID 进入应用。现在已经定位本次挂起的具体阻塞链路：并发认证使单应用放行请求暂存，直到锁屏／解锁结束相关认证后重试。不是扫描、SwiftUI 或数据库初始化阶段的阻塞。但为何 `loginwindow` 在切换密码验证时接管、为何暂存长期不恢复、是否受系统版本或其他软件影响，仍需调查，不能据此断言所有首次打开问题都有同一根因。

最初十分钟 live watch 在用户实际点击批准前约 23 秒已经结束，且 live 命令达到采集 deadline；结果保留为部分证据，未标为成功复现记录。后续 snapshot 和独立补充的 LocalAuthentication 历史日志覆盖了用户操作。根据这次遗漏，采集脚本增加 `coreauthd` / `coreautha`，并新增历史与实时过滤条件回归测试；补充日志的命令状态须单独记录，不能假称属于旧 manifest。

更新后的采集工具回归测试为 16 项、111 个断言，全部通过。这只验证诊断脚本，不表示启动挂起已修复。系统日志调查的方法参考 [Apple DTS：Resolving Trusted Execution Problems](https://developer.apple.com/forums/thread/706442)；本轮没有执行其中会改变安全状态的建议。

本机锁屏／解锁对照完成：前后 PID、进程启动时间、主程序 SHA256 与文件身份相同，没有重启、重装、强制结束、重新签名或移除 quarantine。恢复后的独立 snapshot 包含 32 项成功命令，14 条连续应用启动事件、同一会话、无 `bootstrapFailed`；进程采样显示正常 AppKit 事件循环，Computer Use 确认 Applications 内的欢迎页已出现。该证据验证启动恢复，不验证磁盘扫描、清理或其他 Mac 的首次安装。

恢复出现后主动中止实时采集，仅停止工具自己的日志子进程。该 watch 如实标记 `interrupted` / `complete: false`，不把它改成完整成功；关键事件已保存，独立恢复后 snapshot 完整成功。原始证据仅留在忽略的本机输出目录，公开文档只保存脱敏后的时序与判断。

当前用户绕过方式：首次安装、已经对该应用点击“仍要打开”并完成身份验证，仍无窗口时，先保存工作，手动按 Control + Command + Q 锁屏，再正常解锁，观察已有应用是否打开。本机这次有效，不是经过普遍验证的修复；无效时继续采集，不反复清除安全设置。不要将该方法用来跳过正常的单应用批准，不建议关闭 Gatekeeper、SIP 或删除 quarantine。

产品侧应把这条已知问题与绕过步骤放在 README / DMG 安装引导等应用外部材料中，而非声称应用内可以自动修复：这次阻塞发生在应用入口之前，应用自己的代码和提示尚无法执行。尚未修改用户可见的安装引导、发布包或公开上传原始日志；下一步需要验证授权方式及环境差异，再决定引导与发行方案。

## 2026-10-11 深入定位：密码回退与后台指纹识别

用户不接受把锁屏／解锁或购买开发者账号当成解决此缺陷的终点。本轮继续沿同一批原始证据定位，不重置安全数据库，不更改现有安装。

新增证据：

1. `23:11:57.545`，系统明确记录 `FUS is enabled`；`loginwindow` 的 Authentication Hints Provider 排队等待生物识别空闲。
2. `23:11:58.862`，授权界面的 `FallbackButtonPressed` 使 Touch ID 回退到密码。`23:11:58.866`，Touch ID assertion 释放，排队的后台识别随即开始。
3. 新请求为 `UserIdentificationWithBiometrics`，调用者是 `loginwindow`，设置 `disableConcurrentEvaluation = true`；原 `syspolicyd` 放行请求随后被暂存。后台机制记录 `will start matching any user`。
4. Computer Use 只读检查确认，本机“将触控 ID 用于快速用户切换”当前为开启；用户表示平时因指纹识别不成功而使用密码。此反馈解释了为什么会走密码回退路径，不足以证明指纹识别异常本身就是根因。

**工作假设**：密码回退后，快速用户切换相关的后台指纹识别重新获得认证执行权，导致应用放行请求长期等待。Apple 的[触控 ID 与密码设置说明](https://support.apple.com/en-gb/guide/mac-help/-mchl319754b3/mac)确认该开关控制指纹切换账户；它没有确认这个挂起缺陷。未找到与本机完整时序吻合的官方缺陷说明，不将推测写成 Apple 已确认的问题。

其他检查：安装中的主应用和内嵌 CLI 严格深度签名验证通过，动态依赖为系统框架／系统库。当前证据不支持“损坏的签名或外部动态库使应用自身启动死锁”。此外，本机屏幕解锁授权规则含 `CodexComputerUseAuthorizationPlugin` 分支，日志显示其出现在后续解锁期间；尚未找到它参与初始放行挂起的证据。因此该机器不是未经定制的认证环境，不能据一次复现推断所有 Mac；不擅自改写授权规则或移除插件。

### 独立最小程序对照

`scripts/diagnostics/LaunchProbe.m` 仅记录入口、显示说明窗口并允许关闭退出，不含 SpaceJudge 扫描、数据库、CLI、网络或授权调用。`build-launch-probes.rb` 为 A、B、C 生成独立标识和不同主程序校验和，均采用 universal、ad-hoc + hardened runtime，以减少同一程序已经批准造成的干扰。不同标识不能保证所有系统评估缓存都独立。

```sh
/usr/bin/ruby scripts/diagnostics/build-launch-probes.rb /absolute/existing/private/output
```

脚本只构建、校验签名和 DMG，不安装、不启动、不修改 quarantine、不修改设置；输出目录与清单为私密权限，失败记录不覆盖。裸应用暂存在系统临时目录，避开 Documents 的 File Provider 添加 FinderInfo；原诊断安装的有效签名已经验证，不能把这一构建目录问题归为本次安装挂起根因。

后续对照顺序：
